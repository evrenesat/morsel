# Morsel: implementation-ready handoff

## Objective and delivery
Build Morsel: on Android 11+, tapping the launcher icon opens a compact floating card over the real launcher; the user selects 0–16 portions locally and deliberately sends ONE request to one bound PLAF108 feeder. The app honestly separates cloud acceptance from physical completion. It includes a charming original fluffy cat, cup, kibble and bowl. Deliver public source at evrenesat/morsel, green CI, signed installable APK and test/review evidence.

This plan authorizes implementation, public repository creation, CI and APK releases. Implementation is by installed ZCode GLM-5.3-Flash on p100. This is a normal handoff, not an AFlow plan. Use one worker. Supervisor reviews and returns focused fixes.

No Petlibro credentials or actual S21 are provided. Complete and release the software using fake network/emulator tests; label first release prerelease until owner validation. Never invent live fixtures or claim device acceptance. Do not issue physical feeding commands while owner sleeps. Lack of real account access does not block implementing, CI testing or prereleasing the app.

## Fixed scope
Now: one account, single serial-bound PLAF108 (one-time choice if multiple), local cat name, integer portions, lower configurable cap, haptic preference, English/Dutch, light/dark and reduced motion, small setup/settings, real cloud client, fake/demo test path, safe journal, CI and signed APK.
Out of scope: backend, Home Assistant, overlays, widgets, scheduling/administration, camera, pet profiles, graphs, notifications, analytics, billing, delayed feed queue, automatic feed retries, generic workflow system. Sound stays off; do not add sound assets/settings in v1. Do not add infrastructure or a database.

## Submission and recovery: non-negotiable behavior
Use application-scoped Coordinator and tryLock/atomic compare-and-set so duplicate taps are ignored, never queued. Freeze serial, portions and requestId. UI disable and code guard are both required. Validate range in domain and client. Network effects never come from recomposition or animation callbacks.
Preflight reads verify current bound device, online status and auth; at most one re-login/retry for expired reads. Unknown/offline or missing serial blocks submission. Before HTTP write, DataStore transaction durably saves one operation: id, serial, amount, requestId, createdAt, DISPATCHING, baseline history identities when available. Baseline history failure does not invent attribution; retain unconfirmed outcome. Persistence failure prevents send. Keep journal in noBackupFilesDir; do not discard it on logout, rebinding or settings changes.
Dedicated feed OkHttp client: retryOnConnectionFailure(false), followRedirects(false), followSslRedirects(false), no authenticator, no retry interceptors; strict finite timeouts (connect 10s, call 20s). No retry under timeout, I/O error, 5xx, malformed response, cancellation, auth failure or process death. A single send action invokes this client once. Read transport may retry once; write cannot pass through it.
States: READY, DISPATCHING, ACCEPTED_UNCONFIRMED, REPORTED_SUCCESS, REPORTED_MISMATCH, REJECTED, UNKNOWN. Explicit documented API rejection may be REJECTED; unknown codes/errors are conservative UNKNOWN. Auth 1009 returned by write never triggers replay; refresh only as separate read/setup, then deliberate action if definitively rejected. Persist results before presenting final state. A storage error after request means UNKNOWN and journal remains unresolved.
Restore DISPATCHING as UNKNOWN; accepted/unknown/mismatch stay visible across closing/reopening. Never resend. Keep amount selection at zero on fresh session only when no unresolved operation. Rotation preserves current selection. After success show Done and do not rearm Feed in same session. After unresolved outcome show Check status (reads only), Done, and an explicit secondary 'I checked the feeder' acknowledgement explaining duplicate risk before permitting another fresh selection. Acknowledge records resolution, never erases silently. Close/dismiss does not cancel physical action.
Conservative history policy: ONLY a proven matching request/operation ID and serial can establish this operation's completion. Without correlation fields in source/live evidence, show recent feeder records separately as 'Feeder history', never turn time+amount alone into success. Correlated different amount yields mismatch with no automatic top-up. Duplicate/out-of-order records cannot confirm twice. Poll reads at 3,10,25 seconds after acceptance using injectable timing; status check can repeat read-only. On interruption no background queue; next launch can reconcile. No WorkManager.
